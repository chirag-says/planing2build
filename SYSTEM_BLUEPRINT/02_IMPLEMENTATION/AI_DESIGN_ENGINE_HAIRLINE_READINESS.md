### Governing chain (proposed)

Locked requirement (RQ v1) + design brief (only what RQ lacks) → requirement normaliser → architectural intent → constraints → layout solver → HousePlan → validator → deterministic repair → VALID concept plan → 2D editor and 3D view from the same model → optional illustrative reference into the authoritative design workflow (unchanged) → approved drawings → Build Plan → RFQ.

The concept plan stays non-authoritative. It never replaces an approved drawing set, never feeds the BOQ or RFQ directly, and never makes a structural, statutory or approval claim. [REC], consistent with PD-05, PD-06, S35 B.1 and IC 18.2

## F. Why each adopted pattern is useful

| # | Problem it solves in a plan editor |
|---|---|
| E1 | When a wall is being dragged, testing the pointer against the moving preview makes hover jump between the wall and whatever is behind it. Testing against the committed model gives stable picking and matches the rule that the model, not the screen, is the truth |
| E2 | A viewBox in millimetres scales strokes with zoom; a 0.5 mm dimension line would vanish when zoomed out and bloat when zoomed in. Non-scaling strokes keep annotation crisp while walls (filled polygons in mm) scale truthfully |
| E3 | One palette for the whole product; dark mode and future brand colours arrive without touching the plan code |
| E4 | The plan editor and 3D view are client-only; reserving their box prevents the page jumping when they mount |
| E5 | A 3D view left open in a tab should not burn CPU or battery when nothing changes |
| E6 | React 19 StrictMode mounts effects twice in development; a single teardown path prevents duplicated listeners during drags |

## G. What Hairline cannot do

Hairline has no units, no top-down plan mode as a feature, no text, no data model, no selection, no drag, no snapping, no zoom or pan, no polygon operations, and no extension API. Its styling rules forbid fills and per-element colour.

Effort estimate per capability. Sizes are rough, for one engineer, and low confidence: **S** about a day or less, **M** two to four days, **L** five days or more. "Fork" assumes the fork's core has already been freed from the 400 × 320 box and the figure assumptions, itself an **L**.

## H. Final 2D rendering recommendation

1. **Renderer:** React components emitting SVG, written in Plan2Build, no new dependency. A plan has tens to a few hundred elements; SVG gives exact vector output, DOM hit-testing, CSS theming from shadcn tokens, accessibility hooks and print-quality output. Canvas libraries (Konva, Fabric) suit thousands of moving objects and would add a dependency and a second styling system for no gain here.
2. **Geometry source:** the renderer draws only `PlanGeometry` returned by the API (section J). It computes no areas, no wall outlines and no validity.
3. **Units:** viewBox in millimetres; y flipped for screen; display in feet-inches or metres by toggle.
4. **Interaction:** pointer events on the SVG root, a small tool state machine, snapping and guides in the browser for feedback only; every committed change is a typed operation applied by the server (section O).
5. **Hairline's role:** patterns E1 to E6 as conventions; nothing else.

## I. Canonical HousePlan schema

### I.1 Principles

| # | Principle | Consequence |
|---|---|---|
| I-P1 | The HousePlan document is the only source of truth for a design. SVG, PDF, 3D scenes and images are outputs | No renderer writes back geometry. Editor actions are typed operations applied to the document on the server (section O) |
| I-P2 | Real-world units only: integer millimetres | No floats in stored geometry, so equality and containment checks are exact and the same input always gives the same bytes. Feet and inches are a display format |
| I-P3 | Hosted entities are parametric, never free-floating | A door is (wall id, offset along the wall, width). A fixture is (room id, host wall id, offset, side). A floating door or a WC in the wrong room cannot be expressed with coordinates that "look right"; the validator checks the references instead |
| I-P4 | Walls and rooms share one planar graph | Wall nodes are points; walls join two nodes; a room boundary is an ordered cycle of node ids. Moving a node moves every wall and room that uses it, so rooms and walls cannot drift apart |
| I-P5 | Derived values are never stored as truth | Areas, clear dimensions, footprint, buildable envelope, adjacency, circulation graph and dimension chains are computed on every read. Stored copies exist only inside immutable version snapshots, for audit |
| I-P6 | Every requirement-driven element is traceable | Rooms, fixtures and constraints carry the requirement answer key or interpretation item that caused them. Every relaxation is a recorded compromise |
| I-P7 | Versioned schema | `schema_version` is semver. A reader refuses a major version it does not know. Upgrades are explicit migration functions with tests, never silent reinterpretation |
| I-P8 | No structural assertion | Walls carry `structural_role: "UNASSESSED"` and nothing else in v1. The model never states that a wall is load-bearing, a column is adequate or a slab is safe (section W, risk R-07) |

### I.2 Coordinate system

- Plot-local Cartesian frame, origin at plot vertex 0, x to the right, y up (mathematical convention). Polygons are counter-clockwise.
- `site.north_angle_deg`: clockwise angle from the plot's +y axis to true north. Compass directions (for facing and orientation preferences) are derived from it.
- Elevation z is measured from the ground-floor finished floor level (0). Site datum offsets (plinth height) are on the floor record.
- Renderers flip y for screens (section O.3) and map to Y-up for 3D (section P.2). Neither flip is stored.

### I.3 Document outline (schema 1.0.0)

Field types: `mm` is an integer number of millimetres; `id` is a short string unique within the document (`room_3`, `wall_12`), stable across edits; `ref` is an `id` of another entity.

```text

  schema_version: "1.0.0"
  meta
    plan_id: uuid                          the design_plans row
    project_id: uuid
    requirement_version_id: uuid           the locked requirement answers this plan was built from
```

## J. Deterministic geometry engine

A pure Python package inside the new backend module (section R.1), with no I/O. Every function is input → output, so it is unit-testable and the same input yields byte-identical output.

| Part | Responsibility | Notes |
|---|---|---|
| `geom` | Integer-mm primitives for axis-aligned geometry: rectangle and polygon area (shoelace), containment, overlap, shared-edge length, segment-on-segment, point-on-segment, polygon inset for setbacks | About 300 lines written in-house. Exact integer arithmetic. Shapely (GEOS) is deferred to the non-orthogonal plot work (section V); it would add floating-point tolerance questions the MVP does not need |
| `graph` | Builds the planar wall graph from room rectangles: splits edges at T-junctions, merges collinear segments, assigns EXTERIOR or INTERIOR, sets thickness from the ruleset | One implementation, used by generation and by editor operations |
| `derive` | From a HousePlan, computes everything marked "derived" in I.3: room polygons and clear polygons, areas, clear dimensions, adjacency, circulation graph, opening jamb points and swing arcs, fixture footprints and clearance zones, stair flights, dimension chains | Output is `PlanGeometry`, the single geometry payload used by the web 2D renderer, the 3D scene, the PDF and the validator (section P.1) |
| `ops` | Applies typed editor operations to a HousePlan and returns the new plan plus the inverse operation | Shared by the editor, deterministic repair and later natural-language edits (sections M, O) |
| `units` | mm ↔ feet-inches parsing and formatting for API inputs (the requirement form collects feet) | Display formatting in the web app is presentational only |

Clear (carpet) dimensions are derived as the room polygon inset by half of each bounding wall's thickness. Indian practice quotes room sizes as clear inside dimensions, so size constraints in the intent are clear dimensions; the solver converts them with a wall allowance and the validator checks the exact derived values.

## K. Constraint and rule engine

### K.0 Requirement normaliser, design brief and architectural intent

**Where the language model fits.** Every layout-relevant input in RQ v1 is a closed option or a number. A deterministic normaliser maps them to intent completely. A language model would add cost, run-to-run variation and a personal-data surface without adding information. The MVP therefore has **no language model** in the generation path, which also keeps IC 18.6. [REC] The intent schema below has an `interpretation` slot so that later features (free-text notes, natural-language edits) can add model-proposed items, each shown to the homeowner for acceptance and tagged with provenance (AD-07).

**What RQ v1 already gives** (`requirement_questions_v1.json`): plot rectangle (`plot_is_rectangular`, `plot_width_ft`, `plot_depth_ft`), `facing`, `setbacks` (front, back, left, right, or not sure), `floors`, `bedrooms`, `bathrooms`, `pooja_room`, `car_parking` (yes or no), `vastu` (must follow, where possible, not needed), `built_up_area_sqft`. `style` and `quality_tier` do not affect layout.

**What it lacks** (none of these keys exists in v1): road side as distinct from facing, road width, corner plot, living and dining arrangement, kitchen type, attached versus common bathrooms, number of parking spaces, staircase, utility, room-size preferences. RQ v1 is locked; changing it needs a new version with Chirag's approval (RQ:8).

**Design brief [REC] (AD-03).** A short form shown once, the first time the homeowner presses Generate My Design. It shows the facts already known from the requirement as read-only lines with a link to change the requirement, and asks only what is missing or "not sure". Answers are stored per project and versioned, prefilled on every later generation, and never asked again unless the requirement changes. It is a data-defined question set rendered by the existing wizard field components. Proposed wording is in section X (AD-03).

**Normaliser mapping (deterministic):**

| Source | Intent |
|---|---|
| `plot_width_ft`, `plot_depth_ft` | Plot rectangle in mm (× 304.8, rounded to the mm) |
| `plot_is_rectangular = false` | Not supported in v1: the homeowner is told plainly; nothing is generated |
| `facing` | Entry edge and `north_angle_deg`, reading "facing" as the side the road and main entrance face (AD-15) |
| `setbacks` | Per-edge setbacks; FRONT is the entry edge. NOT_SURE is asked in the brief or taken from a published ruleset table (AD-05); never guessed |
| `floors` | MVP generates only when floors = G (AD-04) |
| `bedrooms`, `bathrooms` | ROOM_PRESENT counts; 5_PLUS asks the exact number in the brief; attached and common split from the brief |
| `pooja_room = yes` | ROOM_PRESENT PUJA |
| `car_parking = yes` | PARKING with the space count from the brief |
| `vastu` | Orientation preferences: off, soft, or soft with high weight; never HARD, and the plan never claims Vastu compliance (AD-13) |
| `built_up_area_sqft` | Soft target for total built-up area; a warning if the envelope cannot hold it |

**ArchitecturalIntent (versioned, stored with each generation):**

```text
ArchitecturalIntent
  intent_version: "1.0.0"
  sources: { requirement_version_id, brief_version_id, ruleset_version }
  site: { plot_mm: {w, d}, entry_edge, north_angle_deg, setbacks_mm: {front, back, left, right}, road_width_mm | null }
  programme: [ { key, room_type, count, size_pref: {w_mm, d_mm} | null, must_have: bool, origin } ]
  relations: [ { kind: ADJACENT_WITH_DOOR | ADJACENT | NOT_ADJACENT_DOOR, a, b, strength, origin } ]
  orientation: { mode: OFF | SOFT | SOFT_HIGH, sectors: [ { room_type, sectors[] } ] }
  parking: { spaces, kind, placement }
  stair: { required: bool, to: ROOF | UPPER_FLOOR, placement: INTERNAL | EXTERNAL } 
  priorities: [ ... ]   from the brief, ordered
  interpretation: [ ]   empty in the MVP; later, model-proposed items awaiting acceptance
```

The homeowner sees this as plain sentences before generation ("3 bedrooms, the main one with an attached bathroom; 1 common bathroom; kitchen next to dining; parking for 1 car on the east side"), with an edit link to the brief.

### K.1 Separation

Architectural rules are data plus small check functions, never prompt text. The LLM does not see or apply them. Three layers:

1. **Ruleset** (data): numeric thresholds and tables. Versioned and approved like the rate card (BP-06 pattern): draft, approved, published; a plan records the ruleset version it was generated and validated against.
2. **Constraint compiler** (code): turns the architectural intent plus the ruleset into the plan's `constraints` list (I.3), each with origin and strength.
3. **Checks** (code): one function per validation code (section L), reading thresholds from the ruleset.

### K.2 Constraint kinds (v1)

| Kind | Strength | Example origin |
|---|---|---|
| ROOM_PRESENT (type, count) | HARD | Requirement: bedrooms = 3 |
| ROOM_MIN_SIZE (width, depth, area) | HARD | Ruleset minimums, or the requirement's preferred size if larger and marked must-have |
| ROOM_PREF_AREA | SOFT | Requirement preferred size |
| ADJACENT_WITH_DOOR (a, b) | HARD | Attached bathroom to master bedroom |
| ADJACENT (a, b) | SOFT | Dining next to kitchen |
| NOT_ADJACENT_DOOR (a, b) | HARD | No WC door opening into kitchen (ruleset) |
| ON_EXTERIOR (room, min_edge_mm) | HARD for habitable rooms and kitchens, SOFT otherwise | Ruleset: light and ventilation |
| IN_DIRECTION (room, compass sector) | SOFT | Vastu preference, only when the homeowner asked for it |
| ENTRANCE_ON_EDGE (edge or compass) | HARD if stated, else SOFT toward road | Requirement: plot facing, road side |
| WET_CLUSTER (rooms) | SOFT | Ruleset: shared plumbing walls |
| PARKING_IN_ZONE | HARD | Requirement plus ruleset placement options |
| INSIDE_ENVELOPE | HARD | Setbacks |
| STAIR_REQUIRED (to_floor) | HARD when floors > 1 or roof access is requested | Requirement: floors, staircase |

### K.3 Ruleset content

Ruleset values are **not** set by this document. Typical items: minimum room dimensions and areas per room type; minimum door widths per opening use; minimum passage width; wall thicknesses (exterior, interior); default floor-to-floor height and plinth; window-to-floor area ratio for habitable rooms; fixture catalogue sizes and clearances; fixture templates per room type; the fixture permission matrix (I.5); setback tables by plot size and road width; parking space size.

Source for each value: the National Building Code of India 2016 Part 3, and the development control rules that apply in Raipur (Chhattisgarh Bhumi Vikas Niyam and any municipal amendments), checked by a qualified architect. Until a value has a cited source and approval, the ruleset is marked DRAFT and plans generated against it carry the label "Rules not yet verified" (decision AD-05, section X).

## L. Validator

### L.1 Design

- Pure function `validate(plan, ruleset) -> ValidationReport`, independent of the generator. It recomputes everything from the document; it never trusts values the generator wrote. A generator bug is therefore caught, not repeated.
- A registry of checks, each with: `code`, `category`, `severity`, the ruleset keys it reads, and a function that returns issues.
- Runs after every generation, every repair pass, every editor operation batch, and before any export or "use as reference" action.
- Plan status: `VALID` when there are zero ERROR issues; `INVALID` otherwise. WARNING issues are shown but do not block. Nothing INVALID is ever labelled ready, exported, or offered as a design reference.

### L.2 Report format

```json
{
  "valid": false,
  "plan_id": "…", "revision_no": 14, "ruleset_version": "2026.1-draft",
  "errors": [
    {
      "code": "FIXTURE_NOT_PERMITTED_IN_ROOM",
      "category": "FIXTURES",
      "severity": "ERROR",
      "entities": [ {"kind": "fixture", "id": "fx_12"}, {"kind": "room", "id": "room_living"} ],
      "message_key": "design.validation.fixture_not_permitted",
      "params": { "fixture_type": "WC_WESTERN", "room_type": "LIVING" },
      "message": "A WC is not permitted in the living room.",
      "repair": "AUTO"

    {
      "code": "ROOM_OVERLAP",
      "category": "GEOMETRY",
      "severity": "ERROR",
```

## M. Generate → validate → repair loop

```text
requirements (locked version)
  → normalise (deterministic) ─┐
  → interpret free text (LLM, optional) ─┴→ ArchitecturalIntent (validated schema, user-visible)
  → feasibility pre-check ── fails → INFEASIBLE with explanation (no plan)
  → compile constraints (K)
  → solve layout (N)  ── no solution → relax SOFT constraints in priority order, recording compromises
                      ── still none → INFEASIBLE with the conflicting HARD constraints listed
  → derive walls, openings, fixtures (J)
  → validate (L)
  → deterministic repair, at most 3 passes, each pass must strictly reduce the error count
  → validate
  → VALID  → stored as a version, shown with any compromises
  → INVALID → not shown as a result; job ends FAILED (reason ENGINE_INVALID_OUTPUT) with the issue list kept internally; credit returned; alert raised as an engine defect
```

| Rule | Detail |
|---|---|
| Deterministic repairs are operations | Each repairer emits typed operations (O.4) logged with reason `AUTO_REPAIR` and the issue code. Examples: DOOR_OUTSIDE_WALL → slide the door inside the wall; FIXTURE_OVERLAP → move the later fixture to the next template slot; FIXTURE_BLOCKS_OPENING → move the opening along its wall; ROOM_ABOVE_MAX_AREA → move the wall shared with a circulation space |
| Repairs never change requirements | A repairer may move geometry. It may not remove a room, change a room type, change a count, or drop a HARD constraint |
| Requirement changes need the user | When HARD constraints conflict, the job returns INFEASIBLE with the arithmetic (for example: "After setbacks the buildable area is 19 ft 6 in × 31 ft. Three bedrooms, two baths, kitchen and living at their minimum sizes need more than that.") and a list of options from a deterministic table (combine dining with living; make one bath common; reduce a bedroom to the minimum). The user picks; the choice becomes a new intent with origin USER_EDIT |
| LLM reconsideration | Deferred. When added, the LLM may only propose alternative intents from the same option vocabulary, shown to the user for acceptance. It never produces geometry and never applies a change without acceptance |
| Never "ready" when invalid | Generation output is either VALID or a failure. An editor may save an INVALID working revision (the user is mid-edit), shown with highlights, with export and "use as reference" disabled |

## N. Layout solver

### N.1 Options evaluated

| Method | Strengths | Weaknesses | Verdict |
|---|---|---|---|
| Fixed templates (one plan per plot size) | Fast, predictable | Breaks on any plot or programme the template did not anticipate; no adaptation | Rejected as the engine; used as zoning knowledge |
| Rule-based zoning (front, middle, rear bands relative to the road; public to private depth) | Matches how Indian residential plans are organised; explainable | Decides topology, not dimensions | Adopted as stage 1 |
| Guillotine / slicing-tree enumeration | Tiles the envelope exactly; no overlaps by construction | Only guillotine layouts; sizing by proportion often breaks minimum widths | Kept as fallback idea, not built |
| Graph-based (adjacency graph → rectangular dual) | Elegant adjacency guarantees | Complex; many adjacency graphs have no rectangular dual; still needs sizing | Rejected for MVP |
| Metaheuristics (simulated annealing, genetic) | General | Slow, tuning-heavy, no proof of feasibility, reproducible only with care | Rejected |
| Learned generators (House-GAN style) | Varied output | Same failure class as image generation: no guarantees, not explainable | Rejected |
| Constraint programming, OR-Tools CP-SAT | Declarative hard constraints (no overlap, containment, minimum sizes, adjacency, exterior access) plus weighted soft objectives; proves infeasibility; mature | New dependency (wheel plus numpy and protobuf, recent versions also pandas; measure the image size before adopting); must be configured for reproducible results | Adopted as stage 2 |

### N.2 Adopted design: zoning plus CP-SAT plus rule-based derivation

1. **Feasibility pre-check.** Envelope area and dimensions against the sum of minimum room areas, a circulation allowance and wall allowance from the ruleset; longest minimum dimension against the envelope's shorter side. Fails fast with readable arithmetic.
2. **Zoning (rules).** Map the envelope's edges to the road side and compass using `north_angle_deg`. Assign each room a band (front, middle, rear) and preferred side from its zone and the intent (living and parking near the entry edge; bedrooms toward the rear; wet rooms near each other; stair hall near the entrance). Produce a small, ordered set of candidate zonings (mirror left/right, swap middle bands) so the result is deterministic and a second option can be offered.
3. **CP-SAT placement (per candidate).** Integer grid at a ruleset module (proposed 75 mm, about 3 in). Variables x, y, w, h per room. Constraints: containment in envelope; NoOverlap2D; minimum width, depth and area with wall allowance; ADJACENT_WITH_DOOR as a shared edge of at least door width plus jamb allowances; ON_EXTERIOR as contact with the envelope boundary for a minimum length; parking in its permitted zone; total room area equals the footprint (circulation spaces are explicit rooms, so nothing is left unassigned). Objective: weighted soft terms (preferred areas, adjacency, wet clustering, Vastu sectors if asked, compactness).
4. **Reproducibility.** Pinned OR-Tools version, fixed seed, single search worker or a deterministic time limit, stable variable ordering. A golden test asserts identical output for a fixed input on every CI run.
5. **Derivation (rules, section J).** Wall graph from rectangles. Doors: one per required connection, on the shared wall, offset from the nearer junction by the ruleset jamb distance, hinge on the side nearer the corner, swinging into the room being entered, never into a passage below its clear width. Windows: centred on each exterior wall segment of a habitable room or kitchen, sized from the ventilation ratio. Main entrance on the entry edge. Fixtures: per-room templates placed along walls that carry no door, with clearance zones; kitchen counter preferentially along an exterior wall with the sink under a window.
6. **Budget.** Solve time capped per candidate (proposed 5 s, at most 3 candidates). The worker runs one solve at a time on the 2 vCPU VPS (`CLOUD_AND_HOSTING_ARCHITECTURE.md:16`, `:67`), the same concurrency model as PDF rendering.

### N.3 What the solver accounts for

| Input | How |
|---|---|
| Plot and setbacks | Envelope = plot inset by per-edge setbacks; containment constraint |
| Room count and sizes | ROOM_PRESENT expands to one variable set per room; size constraints from intent and ruleset |
| Relationships | Adjacency constraints (hard with a door, soft without) |
| Entrance | ENTRANCE_ON_EDGE pins the foyer or living room to the entry edge |
| Circulation | Explicit PASSAGE / FOYER / STAIR_HALL rooms; reachability is validated after derivation (CP-SAT does not reason about paths) |
| Wet-area clustering | Soft objective on the distance between wet rooms and the kitchen |
| Parking | A PARKING room with space-size minimums in its permitted zone |
| Staircase | A STAIR_HALL room sized from the stair geometry the ruleset produces for the floor-to-floor height |
| Orientation and Vastu | Soft sector preferences, only when the homeowner opted in; unmet ones are reported, never hidden |
| Windows and exterior walls | ON_EXTERIOR constraints |
| User priorities | Weights from the intent; must-haves become HARD |

## O. 2D editor

### O.1 One model, no hidden editor state

```text
editor action (drag, click, form)
  → typed operation(s)  →  POST to the API with expected revision_no
  → server applies ops (J.ops) → validates (L) → derives PlanGeometry (J.derive)
  → response: new revision_no, PlanGeometry, ValidationReport
  → web app re-renders 2D and 3D from that response
```

The browser holds three things: the last server response (the model and its geometry), UI state (selection, tool, viewport, layer visibility), and a transient drag preview drawn as an overlay. The preview is never sent, stored or treated as geometry. Releasing the pointer turns the gesture into an operation; the server's answer replaces the preview. There is no client-side copy of the geometry rules.

Latency: one round trip per committed gesture, not per pointer move. On the existing stack this is a small JSON request; derivation and validation of a single-floor plan are pure in-memory work. Measure p95 at the first checkpoint (section T).

### O.2 Rendering

- React components emitting SVG, written in-house. The viewBox is in millimetres, so zoom and pan change only the viewBox; nothing is re-projected.
- Walls are filled polygons from `PlanGeometry` with openings already cut. Rooms are filled polygons coloured by zone. Doors draw leaf and swing arc; windows draw the standard three-line symbol. Fixtures are a small symbol library drawn in millimetres.
- Hairlines (grid, dimension lines, guides, selection outlines) use `vector-effect: non-scaling-stroke` so they stay one screen pixel wide at any zoom (pattern noted from Hairline, section F).
- Colours come from CSS custom properties mapped to the shadcn tokens already in the web app (pattern noted from Hairline's registry wrapper, section F). Validation highlights use the destructive token.
- Labels: room name, clear dimensions and carpet area, formatted in feet-inches or metres by a user toggle. Values come from `PlanGeometry`, never measured from the SVG.

### O.3 Interaction

- Screen to world: invert the viewBox transform (y flipped). Hit-testing uses world-unit geometry from the committed model, not the moving preview, so hover does not flicker under the pointer (pattern from Hairline rule 01, section F).
- Tools as a small state machine: Select, Pan, Move room, Move wall, Resize edge, Move opening, Add room, Measure.
- Snapping: grid (ruleset module), wall nodes, wall centrelines, and alignment with other nodes on the same axis; guides drawn while dragging.
- Zoom (wheel, pinch), pan (space-drag, two-finger), fit to screen.
- Undo and redo: a client stack of operation batches with their server-computed inverses; undo sends the inverse batch as a new operation (section R.2), so history is linear and auditable.
- Layers: rooms, walls, openings, fixtures, dimensions, labels, validation, grid.
- Keyboard: arrow keys nudge the selection by the snap module; Delete removes; Escape cancels a gesture.

### O.4 Operation vocabulary (v1)

| Operation | Effect |
|---|---|
| MOVE_WALL (wall, delta_mm) | Moves a wall perpendicular to itself; its nodes move; attached walls stretch; room boundaries follow because they reference nodes |
| MOVE_NODE (node, dx, dy) | Advanced; axis-locked in v1 |
| ADD_ROOM (type, rect inside an existing room) | Splits the host room with new walls |
| DELETE_ROOM (room, merge_into) | Removes the dividing wall(s); merges into a neighbour |
| SET_ROOM_TYPE (room, type) | Changes type; fixture permissions are revalidated |
| RENAME_ROOM (room, name) | Label only |
| ADD_OPENING / DELETE_OPENING / MOVE_OPENING (opening, offset) / SET_OPENING (width, height, sill, hinge, opens_to) | Hosted opening changes |
| ADD_FIXTURE / DELETE_FIXTURE / MOVE_FIXTURE (fixture, wall, offset, side) | Hosted fixture changes |
| REVERT_TO_VERSION (version) | Restores a saved version as a new revision |

Natural-language edits (later) produce the same operations. "Make the kitchen 2 feet wider" becomes a RESIZE intent (room, axis, +610 mm); a deterministic resolver picks the wall to move (an interior wall with slack on the far side); the result is shown as a preview diff and applied only on confirmation.

## P. 2D → 3D architecture

### P.1 One geometry, three consumers

`PlanGeometry` is produced once, by the backend's `derive` step, from the HousePlan. The web 2D renderer, the web 3D renderer and the PDF writer all consume it. Wall pieces around openings, stair flights and room floor polygons are computed in Python once, with tests, so 2D and 3D cannot disagree and no mapping logic is duplicated in TypeScript.

### P.2 Coordinate mapping

| Plan (mm) | 3D scene (metres, Y up) |
|---|---|
| x | X = x / 1000 |
| y | Z = −y / 1000 (so a camera looking down with north up matches the 2D plan) |
| z (elevation from ground FFL) | Y = z / 1000 |

### P.3 Element mappings

| Plan element | 3D | Rule |
|---|---|---|
| Wall (a, b, thickness t, height h, floor FFL f) | One or more boxes | Length L = \|b − a\|; rotation θ = atan2(b.y − a.y, b.x − a.x) about Y; each box spans a sub-interval [s0, s1] along the wall, centred on the centreline, size (s1 − s0) × height × t, base at f |
| Door in a wall (offset o, width w, height hd) | Gap in the wall | Wall split into: solid [0, o]; lintel piece [o, o + w] from f + hd to the wall top; solid [o + w, L]. Door leaf: a thin box hinged at the jamb, rotated to the closed or a fixed open angle by `hinge` and `opens_to` |
| Window (offset o, width w, height hw, sill s) | Gap plus sill and lintel | Pieces: solid [0, o]; sill piece [o, o + w] from f to f + s; lintel piece [o, o + w] from f + s + hw to the top; solid [o + w, L]. Glazing: a thin transparent plane in the gap |
| Room polygon | Floor slab and ceiling | Floor: polygon extruded by slab thickness, top at f (wet rooms dropped by the ruleset sunk depth, if set). Ceiling plane at f + clear height, hidden in the cut-away view |
| Stair (shape, width, riser r, tread g, risers n) | Steps | Step i is a box g × r × width at height f + i·r, advancing along the run axis; landings as boxes; total rise n·r is checked against floor-to-floor by the validator before 3D ever sees it |
| Fixture | Simple massing block | Box of catalogue w × d × a type height (WC 0.4 m, counter 0.85 m, …) from the ruleset catalogue; no imported meshes in v1 |
| Plot and envelope | Ground plane and setback lines | Plot polygon as a flat plane; envelope as an outline |

No CSG library is needed: openings are made by splitting walls into pieces, which is exact for straight walls.

### P.4 Library choice

| Option | Fit with the web app (Next.js, React) | Size and cost | Verdict |
|---|---|---|---|
| three.js alone | Imperative; needs a hand-written React wrapper and teardown | About 150 kB gzipped core | Possible, more glue code |
| three.js + React Three Fiber | Declarative scene from props, so the scene re-renders from `PlanGeometry` like any React view; `frameloop="demand"` draws only when something changes | three.js plus a small renderer | **Recommended** |
| Babylon.js | Strong engine with its own inspector and physics | Larger bundle; not React-shaped; more than this feature needs | Rejected |

Controls: OrbitControls for orbit and zoom; first-person walkthrough with pointer-lock controls and eye height 1.6 m, without collision in v1. Import controls from three's own examples rather than adding `@react-three/drei`, unless a later need justifies it. The 3D view loads lazily (`next/dynamic`, no server render) so it costs nothing on pages that do not open it.

## Y. Final recommendation and verdict

### Recommendation

1. Treat the HousePlan as the product. It is a versioned JSON document in integer millimetres, owned by a new backend module. Walls, rooms and hosted elements share one planar graph, so floating doors, wrongly placed fixtures and rooms detached from walls cannot be expressed.
2. Generate geometry deterministically: rules decide zoning, CP-SAT decides placement and size, and rules derive walls, openings and fixtures. No model writes coordinates, and the MVP uses no language model at all.
3. Validate independently of the generator, with machine-readable codes tied to entities. Never present an INVALID plan as a result.
4. Repair deterministically through the same operations the editor uses. Never change a requirement without the homeowner choosing it.
5. Derive `PlanGeometry` once, in Python, and feed it to the 2D SVG editor, the three.js / React Three Fiber view and the fpdf2 PDF. 2D and 3D therefore cannot disagree.
6. Keep 3.1 concept images as optional look-and-feel. Keep the authoritative design workflow, Build Plan and RFQ unchanged.
7. Build the 2D renderer in-house. Take six rendering patterns from Hairline as conventions and nothing else.

### Verdict

**BUILD WITHOUT HAIRLINE**

Technical justification:

- Hairline is a set of 27 fixed decorative isometric illustrations with a private core. A floor-plan editor needs millimetre units, a top-down view, text, a data model, selection, drag, snapping, zoom, polygon operations and colour-coded validation. Hairline has none of these, and its own rules forbid fills and per-element colour.
- Forking it would retain about 620 lines of core and then replace the coordinate box, depth model, pointer model and styling rules. Every capability in section G costs the same or more inside a fork than in Plan2Build's own renderer, plus the cost of freeing the core.
- The renderer Plan2Build needs is small, because the backend derives all geometry. It is an SVG painter with a pointer state machine. It needs no third-party code, and its correctness is tested where the geometry lives.
- The MIT license would allow reuse. Nothing is worth reusing beyond ideas, so the clone stays in `REFERENCE/` as a study.
